# Android app and F-Droid

The native Android app is distributed through **[F-Droid](https://f-droid.org)**, the free and open-source
app store, and as a signed APK on each GitHub release (see *GitHub releases* below). F-Droid builds every app itself from the published source code, signs it, and rejects apps that contain
proprietary code.

## What keeps the app F-Droid-compatible

- **No proprietary dependencies.** `expo-camera` was removed because its Android barcode scanner uses Google ML
  Kit. Transfer QR codes are web links instead, so any camera app can open them (see
  [progress-transfer.md](progress-transfer.md)). Unused template modules (`expo-device`, `expo-web-browser`,
  `expo-symbols`, `expo-glass-effect`, `@expo/ui`) were removed too.
- **Dependency scan (2026-10-29):** `./gradlew :app:dependencies --configuration releaseRuntimeClasspath` contains
  no `com.google.android.gms`, Firebase, ML Kit, Play libraries, install referrer or analytics.
  Rerun this check after adding any native module:
  ```bash
  cd android && ./gradlew :app:dependencies --configuration releaseRuntimeClasspath -q \
    | grep -iE "gms|firebase|mlkit|play-services|com.google.android.play|installreferrer|analytics"
  ```
- No network access is needed for app features, there's no telemetry, and no runtime permissions are requested.
- `EXPO_NO_TELEMETRY=1` is set in the build recipe.

## Building the release APK locally

Requirements: Node 22 or 24, JDK 17, the Android SDK (`ANDROID_HOME`). Gradle downloads NDK, CMake and build-tools on
first run.

```bash
export ANDROID_HOME=$HOME/Library/Android/sdk          # adjust for your OS
npm run android:release
# → android/app/build/outputs/apk/release/app-release.apk
```

`android/` is generated by `expo prebuild` (Continuous Native Generation) and is git-ignored; never edit it by hand.
Configure native behavior in `app.json`. The version comes from `app.json`: `expo.version` (versionName) and
`expo.android.versionCode`.

`EXPO_PUBLIC_WEB_APP_URL` (committed in `.env`, `https://astanov.com/burgerweg/app`) makes transfer QR codes in
the Android app point to the hosted web app, and it also declares the App Links intent filter for
`<that URL>/transfer` (`app.config.js`), so scanned codes open the app. Expo loads `.env` for every build, so no
command needs the variable; an environment variable of the same name overrides it. Without any value, the app shows
the bare `EBT1.` code (still works when pasted) and claims no links. After F-Droid's first build, publish F-Droid's signing fingerprint in `assetlinks.json` (see
progress-transfer.md).

If `ANDROID_HOME` isn't set in your shell, Gradle fails with "SDK location not found". Add
`export ANDROID_HOME=$HOME/Library/Android/sdk` to `~/.zshrc`. `android:release` first deletes Metro's cache (`<tmp>/metro-cache`), because a stale cache can keep an old
`app.json` (e.g. the previous version number) inlined in the bundle. Don't run two builds at once: `npm run
android:release` regenerates `android/` (`prebuild --clean`) and breaks a build already running there.

Locally the release APK is signed with the debug key from the template. That's fine for testing; F-Droid re-signs
with its own key.

## Verified (2026-10-29)

- `assembleRelease` builds successfully (Expo SDK 58, React Native 0.88, JDK 17).
- On the Android 16 emulator, the release APK installs, shows the Bürgerweg icon and name in the app drawer, starts
  without a dev server, and onboarding (single-column state list) leads to the dashboard. No crashes in `logcat`.
- **Size:** the universal APK is about **106 MB**, because it contains native libraries for four ABIs (`arm64-v8a`,
  `armeabi-v7a`, `x86`, `x86_64`); the app's own content is ~2 MB. Before publishing, consider per-ABI APKs (ABI
  splits, each with its own versionCode), which F-Droid supports and which would be roughly a quarter of the size.

## Build recipe

`fdroid/com.buergerweg.app.yml` is the recipe to copy into fdroiddata as `metadata/com.buergerweg.app.yml`. Keep it
free of comments: `fdroid lint` rejects comment indentation (`comments-indentation`) and `fdroid rewritemeta` drops
comments anyway. Notes that used to live in it:
- `sudo` installs Node 24.22.2 from the official tarball (checksum pinned): React Native 0.88 needs `^22.13` or `^24.3`, and the build image (Debian trixie) ships Node 20. Debian stable has no patched Node ≥ 22, and 24.22.1 is the first 24.x with the Brotli fix for CVE-2026-111497. `ndk: r27b` is the NDK React Native asks for (27.1.12297006).
- `sudo` also installs JDK 17 from `bookworm-security` and makes it the default: React Native's Gradle plugin and Expo modules ask for a Java 17 toolchain, and trixie only ships JDK 21. Plain `bookworm` has an older JDK 17 (17.0.19), so the security suite is needed for the patched 17.0.21. `prebuild` installs CMake 3.22.1, the version the local build uses.
- No `subdir`: `android/` is generated by `expo prebuild` in `init`, and F-Droid checks `subdir` before `init` runs
  ("Missing subdir").
- `build: cd android && gradle assembleRelease`: the scanner deletes the generated Gradle wrapper (`gradlew` and its
  jar), so the recipe calls `gradle`, which is F-Droid's verified `gradlew-fdroid` on the build server. It must know
  the Gradle version in `android/gradle/wrapper/gradle-wrapper.properties`.
- `init` removes the debug signing from the generated release build type (`sed … android/app/build.gradle`), so
  `output` is the unsigned APK that F-Droid signs.
- Keep lines short: Homebrew's fdroidserver 2.4.x `rewritemeta` wraps long lines with trailing spaces, which `lint`
  then rejects. `UpdateCheckData` reads the versionCode from `app.json` and takes the version name from the tag.
- `scanignore: node_modules` is a starting point; reviewers may instead ask to `scandelete` or build React Native's
  prebuilt binaries (e.g. `hermesc`) from source.

Check it from your fdroiddata checkout (with an app ID, so other apps' metadata isn't parsed; Homebrew's
fdroidserver 2.4.x is too old for current fdroiddata as a whole):
`fdroid lint com.buergerweg.app`, `fdroid rewritemeta com.buergerweg.app`, `fdroid build -v -l com.buergerweg.app`.

## Store listing

`fastlane/metadata/android/{en-US,de-DE}/`: `title.txt`, `short_description.txt` (≤ 80 chars),
`full_description.txt` (simple HTML), `changelogs/<versionCode>.txt`, `images/icon.png` (512×512) and
`images/phoneScreenshots/1-4.jpg`. F-Droid reads these straight from the repository.

## Publishing on F-Droid: checklist

1. Publish the repository (Codeberg, GitLab or GitHub) and tag the release: `git tag v1.2.0` (the current `expo.version`).
2. Copy `fdroid/com.buergerweg.app.yml` into fdroiddata's `metadata/` and run `lint`, `rewritemeta` and `build`.
3. Fork <https://gitlab.com/fdroid/fdroiddata>, add the file as `metadata/com.buergerweg.app.yml`, and open a merge
   request. Test it locally with `fdroid build -v -l com.buergerweg.app` in the fdroidserver Docker image if you can.
4. Expect review questions about **React Native's prebuilt binaries** in `node_modules` (for example `hermesc`) and
   about the Node.js version on the build server. The recipe is a **draft**; the reviewers' guidance decides the
   final `sudo`/`init`/`scandelete` lines. Other React Native apps on F-Droid are useful references.
5. After the first release, add `changelogs/<versionCode>.txt` for every new version and bump `versionCode`.

**While F-Droid review is pending:** the signed APK on GitHub releases is the way to install the native app. The
IzzyOnDroid F-Droid-compatible repository could also pick up those APKs (optional).

## GitHub releases

`.github/workflows/release-apk.yml` runs when a tag `v*` is pushed. It builds the APK the same way as the F-Droid
recipe (Node 24.22.2, JDK 17, `npm ci --ignore-scripts`, prebuild, the debug signing removed, `assembleRelease`),
then aligns it (`zipalign -P 16`, 16 KB pages), signs it with the release key (`apksigner`) and attaches
`buergerweg-<version>.apk`, its `.sha256` and a copy named `buergerweg.apk` to the release of that tag. The landing
page's download button links to `<repo>/releases/latest/download/buergerweg.apk`, which GitHub always resolves to the
newest release, so the site needs no rebuild per release (and no JavaScript). Until a release has `buergerweg.apk`
(1.6.0 onwards), that link returns 404, so tag right after merging. The release notes are the en-US changelog
of the versionCode. The job fails if the tag doesn't match `expo.version` in `app.json`, so bump first, then tag.
The job summary prints the signing certificate's SHA-256.

Third-party actions are pinned to full commit hashes (with the version in a comment); update them deliberately
after checking their advisories. The workflow token only gets `contents: write`.

**One-time setup of the release key** (keep the keystore and password safe and backed up: an app signed with a lost
key can never be updated in place, users would have to uninstall first):

```bash
keytool -genkeypair -keystore buergerweg-release.keystore -alias buergerweg \
  -keyalg RSA -keysize 4096 -validity 10000 -dname "CN=Bürgerweg"
base64 -i buergerweg-release.keystore | pbcopy          # macOS: copies the keystore as text
keytool -list -keystore buergerweg-release.keystore     # shows the SHA-256 fingerprint
```

Then in the GitHub repository: *Settings → Secrets and variables → Actions → New repository secret*:

| Secret | Value |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | the base64 text copied above |
| `ANDROID_KEYSTORE_PASSWORD` | the keystore password chosen in `keytool` |
| `ANDROID_KEY_ALIAS` | `buergerweg` |

Keep the keystore file outside the repository (`*.jks` and `*.keystore` are ignored anyway). Add the fingerprint to
the Cloudflare build variable `ANDROID_CERT_SHA256`, comma-separated next to the existing ones, so transfer links
open the GitHub-installed app too (see progress-transfer.md).

**Different signatures:** F-Droid signs its builds with its own key, so an APK from GitHub and one from F-Droid
can't update each other; switching means uninstalling first (export progress before). Once F-Droid builds the app,
the build could be made reproducible so F-Droid ships the APK with this release signature instead.

To run it again for an existing tag (for example after adding the secrets), use *Actions → Release APK → Re-run*;
the upload replaces the files (`--clobber`).

## Testing on the emulator

```bash
~/Library/Android/sdk/emulator/emulator -avd <AVD name> &
adb install -r android/app/build/outputs/apk/release/app-release.apk
adb shell monkey -p com.buergerweg.app 1
```

The release build bundles the JavaScript, so no dev server is needed. For live development use `npm run android`
(Expo Go) or `npx expo run:android` (development build).
